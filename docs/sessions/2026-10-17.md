## Decisions taken without the user

Recorded in the README ("Gates", "Review and merge", "Session recovery", "Conventions", "The `crew` CLI") and open to overrule:

- Only the final `down` removes images. The gate's opening `down` keeps them, because it runs right before `build`, which replaces them anyway.
- `crew env down` keeps its images, so a Dev's next `crew env up` is fast; the README now says so in the command table.
- `--rmi local`, not `--rmi all`, so images that `compose.yaml` pulls by name stay.

- #23: a gate worktree kept after a failed teardown is retried by the leftover removal only once its ticket leaves stages 4 to 6, as the README's leftover rule says; until then the ticket's next gate run takes the project down first. The leftover removal does not look at `.crew/worktrees/gate/doctor`; the next `crew doctor` handles it.
- #23: `crew doctor` reports the teardown failure with the log path, not the end of the `down` output, because it prints one line per check.
- #23: `crew ticket submit` exits 0 when only the teardown failed, so a Dev does not resubmit a gate that passed.

## Native Windows support

Decided with the user: all three install methods work from PowerShell; Windows installs to `~\.local\bin\crew.exe`; releases add `crew-windows-amd64.exe` and `crew-windows-arm64.exe`; the release workflow runs the tests on a `windows-2025` runner before it releases.

- `scripts/go.ps1` and `scripts/self-build.ps1` mirror the `sh` scripts; `go.ps1` reads the image pin from `go.sh`. Run under `pwsh` 7.6.7 on Linux with Podman, `self-build.ps1` built the same `crew-windows-amd64.exe` bytes as `self-build.sh`.
- `.gitattributes` checks text out with LF, so a Windows checkout with `core.autocrlf` embeds the same files and builds the same bytes.
- The bootstrap's release block was run under `pwsh` against the real `v0.1.1` release, with the Linux asset name swapped in: it installed, refused a tampered binary, and refused a wrong `--source-ref`.
- `internal/github/exec_test.go` uses the test binary as its `gh` stub, not a `/bin/sh` script. Git hooks in tests stay shell scripts: Git for Windows runs them.
- The test suite passes on the `windows-2025` runner, and Windows PowerShell 5.1 parses the scripts and the bootstrap blocks. The first run found two real faults, both fixed: git prints forward-slash paths, which mixed with `filepath.Join` paths, so `git.Toplevel` and `git.MainRoot` now return native paths; and on Windows a reader of `.crew/lead.lock` made a concurrent `os.Remove` fail, so the lock and the event files are read with `FILE_SHARE_DELETE` (`internal/sharedfile`). The runner's default `TEMP` has 8.3 short names that git expands, so the Windows tests run with `TEMP` set to `runner.temp`. Run by hand, the release workflow runs only the Windows tests.
- Not yet run on a Windows machine: the bootstrap, a container gate, a field test.
- `v0.2.0` is the first release with Windows binaries and `self-build.ps1`; the Windows blocks in `project/AGENTS.md` need it or later.

## Main instance and the lead DM's work cycle

- `crew main up|down|logs` and a refresh in `crew merge` keep the app running at the head of `main` in compose project `crew-<id>-main`, from `.crew/worktrees/main`. Host ports live in `.crew/ports.toml`, not committed: written once with each published container port as its host port, then only read, and passed to compose as a generated `!override` file bound to `127.0.0.1`. On by default; `crew main down` writes `.crew/main.off`. Named volumes survive refreshes. Profiles without a `run` command (python) have no main instance. Verified with unit tests and by hand on podman-compose 1.6 with the node-ts scaffold: first start, pinned port, refresh to a new commit, a moved port, logs and down. Not verified: Docker Compose (its `ps --format json` is covered by a unit test only), Windows.
- Known trade-offs: `crew merge` waits for the main instance's rebuild; a failed refresh is only a warning on the merge's stderr; the first start, before the ports are pinned, publishes the engine's random ports on all interfaces.
- #28 closed: the lead DM's work cycle is in the DM rules and the README. Each wake: events, merge, start up to the cap, wait. A full `crew status` only at lead start, for a stale handoff or on request, so the lead stays event-driven.
- #29 closed: the README states that the crew works on its own only while a lead session is open and woken, and lists the validated harnesses from the field tests. No `crew doctor` check against the list: it would go stale, and the self-test checks wiring live.
- #26 closed: `crew events` reports `#<n> deployment finished: <conclusion>` for the newest deployment run of an open ticket at `7:merged` or `8:deploying`, timed by the run's `updated_at`. Costs two API calls per such ticket per poll. Not verified on real GitHub: that a completed run's `updated_at` is its finish time and does not move afterwards; a field test with a deployment workflow checks it.
- #25 closed: an operation lock, `.crew/lead.lock.op`, held by every lead-only command except `crew events --wait` and released by the OS when the process ends; `crew merge` re-checks the token before the rebase, the push, the stage move and the cleanup, `crew status --lead` before removing leftovers. Takeover stays instant. Windows tests pass on CI (run 39036861089). Known gap: `crew main up` is not lead-only and takes no lock, so it can race the refresh in `crew merge`; the next `up` repairs that.
- #27 closed: `crew ticket repair` repairs a stage-6 conflict or code-caused gate failure on the same ticket (6 back to 4, same rank, not a failed attempt, worktree rebuilt on `origin/main` with the change uncommitted, lease push on the Dev's first commit, fresh gate and review). The DM never resolves conflicts on the branch: the docs had still allowed it, though `crew merge` refused it since #22. `c68299e` briefly left `main` failing `TestRulesCoverEveryDuty`; fixed in `805c033`.
