## Design rationale

The README records the decisions. These are the reasons behind the ones most likely to be questioned again, and the alternatives that were rejected.

| Decision | Why | Rejected |
| --- | --- | --- |
| Runs inside the user's harness; GitHub and git hold all state | The user wants a simple system. No setup beyond git, a container engine, the harness and `crew`. | A supervisor daemon, a local database or control plane, system services, a GitHub App, long soak tests |
| Guard against honest mistakes, not malicious agents | Real isolation would need separate identities and a supervisor, which breaks simplicity and harness neutrality. | Containerised agents, separate credentials per role |
| Go CLI, embedded profiles and rules | One static binary, cross-platform, testable; nothing copied into user projects. | Shell scripts, Python scripts, no scripts |
| Release binary by default, reproducible self-build as an option | Some users will not trust a downloaded binary. | Fetching from `main` |
| No CI gate; `crew` gates locally on the exact commit | Branch protection is not free on private repositories, CI minutes cost money, and CI adds setup. | GitHub Actions as the gate, branch protection |
| Fast-forward merge of the gated commit | GitHub's rebase merge rewrites commits, so `main` would hold untested commits. | GitHub merge buttons |
| Stage numbers never decrease; one command per stage change | A clear state plus its dwell time shows which handoff failed. | A generic set-stage command |
| Tiers are numbered ranks of model plus effort, escalating by one | Gives the user cost control with simple arithmetic. | Named tiers only, a fixed number of tiers |
| TDD verified by running tests at each red and green commit | The user sees TDD as the main guardrail against agent mistakes; commit messages alone prove nothing. | Checking commit subjects only |
| Binding review, one appeal to a second Reviewer | Independence without letting the DM mark its own work. | DM override, advisory review |
| `crew` does the deterministic work; the DM handles exceptions | Prevents `crew` from growing corner-case machinery. | Encoding every corner case in `crew` |
| Never a victim of its own workings | No lock or limit may stall the crew; every one recovers with at most a user confirmation. | Liveness detection by heartbeats or timeouts |
| Harness wiring written by the agent against a contract | Each harness differs; the agent knows its own. A long polling loop in one session grows context without bound. | Shipping adapters per harness, a polling loop in the lead DM's context |
| `crew events --wait`, checked by a self-test at every lead DM start | Claude Code and OpenCode both wake an agent when a background command exits, so one blocking command is the whole wiring there. | A hand-written polling loop per harness, `crew doctor` doing the live test (it cannot see whether a session woke) |
| The lead DM is one long session | A one-off session cannot exit while its subagents run, and they stop when it ends. Compaction is safe because all state is on GitHub. The user starts a fresh session to save tokens. | A fresh session per event |

## Open: harness wiring feasibility

The design depends on one unproven assumption: that a harness can wake the lead DM when an event happens, without growing its context while idle and without any process outside the harness session. See "Keeping the lead DM running" in the README.

Claude Code and OpenCode have each been tested cleanly with the revised prompt below, one at a time and in separate directories. Codex has not, and the test is skipped: with the self-test, a Codex lead DM finds out at its first start, and either result leads to working wiring. A run on native Windows failed, because the prompt assumes a POSIX shell (`bash`, `mktemp`, `/tmp`, `sleep`, `ps`). Windows is supported only through WSL, so any later Codex test must run inside WSL.

### Results

| Capability | Claude Code 2.1.296 (VS Code, Linux) | OpenCode 2.0.28 (Linux) |
| --- | --- | --- |
| Subagent completion wakes the lead | Yes. Two background subagents ran in parallel; one completion notice each, no user message. | Yes. Same result. |
| External event wakes the lead | Yes, about 6 seconds after the event. | Yes, about 1 to 2 seconds after the event. |
| Context growth while idle | Zero over 10 minutes 40 seconds. | Zero over 10 minutes. |
| Fresh context per event | Yes: `claude -p "<prompt>" --no-session-persistence --allowedTools ... < /dev/null` | Yes: `opencode run '<prompt>' < /dev/null` |
| Conversation while waiting | Yes; the next event still woke the lead. | Yes; the next event still woke the lead. |
| Wiring stops with the session | Yes. The loop is a child of the session's `claude` process. SIGTERM to a stand-in `claude -p` session killed its loop too. | Probably not. The loop's parent is `opencode serve --service`, a service that had been running for two days. The chat client process is separate. |

### The wiring both harnesses used

Neither harness needed hooks, plugins or settings files. Both use the same mechanism: the lead starts a shell command in the background that polls and exits when there is something new, and the harness wakes the lead when a background command exits.

```sh
while :; do out=$(./events.sh); [ -n "$out" ] && { printf '%s\n' "$out"; exit 0; }; sleep 2; done
```

The command wakes the lead once. The lead handles the work and starts the command again, so each event costs one tool call. Neither harness includes the command's output in the exit notice, so the lead reads the events with one more call.

### Limitations found

- Claude Code: a `claude -p` session does not exit while it has a background task running; it hung until it was sent SIGTERM. A lead that starts Devs and Reviewers as background subagents therefore cannot run as one short session per event. This affects contract point 2 ("prefer fresh context").
- Claude Code: the `Monitor` tool wakes the lead once per output line, but each watch expires after at most 30 minutes, so it costs a turn every 30 minutes while idle. `CronCreate` only re-runs a prompt on a schedule and cannot react to an event. Neither is a better choice.
- OpenCode: a waiter left behind when a session ends keeps running inside the service. When the next event arrives, it marks that event read and wakes no one, so the next lead never sees it in `crew events`. `crew status` still rebuilds the full state from GitHub, so no work is lost, but no one is woken for that event.
- OpenCode: starting a second waiter gives two pollers and two wake-ups. Nothing prevents it.
- OpenCode: `opencode run` uses the project's default model and agent unless `--model` and `--agent` are passed.

### Still unknown

- Whether a background command has a maximum lifetime, in either harness. The longest observed ran 10 minutes 40 seconds.
- What happens to the waiter when the session is actually closed: the VS Code panel for Claude Code, the session for OpenCode. Both runs only inferred it, from a SIGTERM stand-in and from process ancestry.
- Whether a one-off `opencode run` session exits while it has background subagents running.
- Whether an event that arrives before the lead restarts its waiter is caught at once by the next waiter. The offset design implies it is, but neither run tested it.

### Decided: `crew events --wait` and a self-test at every lead DM start

Recorded in "Keeping the lead DM running" in the README. In short:

- `crew events --wait` blocks until something is unread and exits without marking it read. A newer wait replaces an older one. This makes a wait left behind in OpenCode's service harmless, which settles the OpenCode question without changing contract point 3.
- Every lead DM session looks its harness up in `.crew/crew.toml`. A harness that is not recorded gets a self-test with `crew events --wait --test`. On success, the record says the harness supports `--wait`. On failure, the lead DM writes its own wiring, which you confirm, and records that.
- A failed self-test cannot be noticed by the DM, because it is never woken. So before the test it asks you to send any message if it has not continued within a minute.
- A stale record shows up as events that should have woken the lead DM. The lead DM then re-tests.

Contract point 2, "prefer fresh context", was dropped. A one-off session cannot exit while its background subagents run, and Devs and Reviewers stop when the lead DM's session ends, so a fresh session per event could only handle work that starts no subagents. The lead DM is one long session instead, and starting a fresh one to save tokens is up to the user.

Left for the implementation plan: how the lead DM commits a change to `.crew/crew.toml`, and how a replaced `--wait` finds out it has been replaced.

## Background

A tool called `crew` (not yet built) will coordinate AI agents. One agent, the "lead", must react to events (a subagent finishing, new work appearing) without a human prompting it, and without its context growing while it is idle. No daemons are allowed outside the harness: no cron, systemd, launchd, or processes that outlive this session. The question is what THIS harness can do natively.

## Setup

1. Create a unique directory for this run and work only there:
   `d=$(mktemp -d /tmp/wake-test.XXXXXX) && cd "$d" && pwd`
   Tell me the path. Never touch any other /tmp/wake-test.* directory.
2. Create a simulated event source, since `crew` does not exist yet. Both scripts must locate files relative to their own directory and contain no hard-coded paths:
   - `fire.sh "<text>"` appends one line, `<ISO-8601 UTC timestamp> <text>`, to `events.log`.
   - `events.sh` prints the lines of `events.log` added since its previous call, then exits. It tracks progress as a LINE count in `events.offset`, and prints nothing if there is nothing new.
   Make both executable.

## Rules

## Tests

Run these in order. For each test, record what you did, what happened and the timestamps.

1. **Subagent completion.** Start two subagents. Each waits about 60 seconds (for example `sleep 60`), then replies "done". Then end your turn immediately. Questions: Are subagents synchronous (your turn blocks until they return) or asynchronous? If asynchronous, are you woken automatically when each one finishes, with no message from me? Did they run in parallel?

2. **External event wake.** Design and, after my approval, install the lightest wiring this harness supports that wakes you when `events.sh` has output. Then end your turn and tell me the `fire.sh` command to run from another terminal. Questions: Did you wake by yourself? How long after the event? What triggered it?

3. **Idle cost.** Stay idle for 10 minutes with no events. Questions: How many turns, tool calls or messages were added to your context in those 10 minutes? The goal is zero, or close to it. 4. **Fresh context per wake.** Can this harness start a fresh, short-lived agent session per event, from inside this session, with no external scheduler (for example a headless or non-interactive mode)? If yes, demonstrate it once: when an event arrives, a fresh session runs `events.sh`, writes one line to `handled.log` and exits. Pass the prompt as an explicit argument, and close standard input if the command would otherwise wait for it.

6. **Lifetime and cleanup.** Find out which process actually runs your wiring: this chat session, a harness server or background service, or something else. Show the evidence (`ps` output, process IDs, parent processes). Then answer: Does the wiring stop when this session ends? If not, what does stop it? Tell me how I stop it now.
