## Design rationale

The README records the decisions. These are the reasons behind the ones most likely to be questioned again, and the alternatives that were rejected.

| Decision | Why | Rejected |
| --- | --- | --- |
| Runs inside the user's harness; GitHub and git hold all state | The user wants a simple system. No setup beyond git, a container engine, the harness and `crew`. | A supervisor daemon, a local database or control plane, system services, a GitHub App, long soak tests |
| Guard against honest mistakes, not malicious agents | Real isolation would need separate identities and a supervisor, which breaks simplicity and harness neutrality. | Containerised agents, separate credentials per role |
| Go CLI, embedded profiles and rules | One static binary, cross-platform, testable; nothing copied into user projects. | Shell scripts, Python scripts, no scripts |
| Release binary by default, reproducible self-build as an option | Some users will not trust a downloaded binary. | Fetching from `main` |
| No CI gate; `crew` gates locally on the exact commit | Branch protection is not free on private repositories, CI minutes cost money, and CI adds setup. | GitHub Actions as the gate, branch protection |
| Fast-forward merge of the gated commit | GitHub's rebase merge rewrites commits, so `main` would hold untested commits. | GitHub merge buttons |
| Stage numbers never decrease; one command per stage change | A clear state plus its dwell time shows which handoff failed. | A generic set-stage command |
| Tiers are numbered ranks of model plus effort, escalating by one | Gives the user cost control with simple arithmetic. | Named tiers only, a fixed number of tiers |
| TDD verified by running tests at each red and green commit | The user sees TDD as the main guardrail against agent mistakes; commit messages alone prove nothing. | Checking commit subjects only |
| Binding review, one appeal to a second Reviewer | Independence without letting the DM mark its own work. | DM override, advisory review |
| `crew` does the deterministic work; the DM handles exceptions | Prevents `crew` from growing corner-case machinery. | Encoding every corner case in `crew` |
| Never a victim of its own workings | No lock or limit may stall the crew; every one recovers with at most a user confirmation. | Liveness detection by heartbeats or timeouts |
| Harness wiring written by the agent against a contract | Each harness differs; the agent knows its own. A long polling loop in one session grows context without bound. | Shipping adapters per harness, a polling loop in the lead DM's context |

## Open: harness wiring feasibility

The design depends on one unproven assumption: that a harness can wake the lead DM when an event happens, without growing its context while idle and without any process outside the harness session. See "Keeping the lead DM running" in the README.

A first experiment ran one test prompt in Claude Code and in OpenCode. Both runs used the same directory, so their files collided and part of the evidence is unreliable.

### Results so far

| Harness | Finding | Confidence |
| --- | --- | --- |
| Claude Code | Background subagents run in parallel, and each one wakes the main agent automatically when it finishes. | Good: two subagents, two automatic wake-ups |
| Claude Code | An external event woke the idle agent about 4 seconds after it fired. | Good, but the wiring used was not recorded |
| Claude Code | Headless fresh-context runs were not tested properly: the `claude --print` calls had no prompt and failed with `Input must be provided either through stdin or as a prompt argument when using --print`. | None; repeat the test |
| OpenCode 2.0.28 | A project plugin can inject a prompt into a session (`ctx.session.prompt`). Its polling runs in the plugin, so it costs the session no context. | Good |
| OpenCode 2.0.28 | The plugin runs inside the long-lived `opencode serve` process, not the chat session. It kept running after the session ended and stops only when that server restarts. | Good |

The OpenCode finding conflicts with contract point 3 ("live inside the harness session"). Decide whether wiring loaded by a harness's own server process is acceptable when it stops with that server, or whether the wiring must detect that its session has ended and stop itself.

### What went wrong in the experiment

- Both runs used the fixed directory `/tmp/wake-test`.
- One run tracked the event offset in bytes and the other in lines, so `events.sh` stopped reporting events.
- The OpenCode plugin replayed the first run's event as new.

## Revised experiment prompt

Give this to a fresh session in the harness under test.

````
You are running a feasibility experiment. Do not build anything beyond what this experiment needs.

## Background

A tool called `crew` (not yet built) will coordinate AI agents. One agent, the "lead", must react to events (a subagent finishing, new work appearing) without a human prompting it, and without its context growing while it is idle. No daemons are allowed outside the harness: no cron, systemd, launchd, or processes that outlive this session. The question is what THIS harness can do natively.

## Setup

1. Create a unique directory for this run and work only there:
   `d=$(mktemp -d /tmp/wake-test.XXXXXX) && cd "$d" && pwd`
   Tell me the path. Never touch any other /tmp/wake-test.* directory.
2. Create a simulated event source, since `crew` does not exist yet. Both scripts must locate files relative to their own directory and contain no hard-coded paths:
   - `fire.sh "<text>"` appends one line, `<ISO-8601 UTC timestamp> <text>`, to `events.log`.
   - `events.sh` prints the lines of `events.log` added since its previous call, then exits. It tracks progress as a LINE count in `events.offset`, and prints nothing if there is nothing new.
   Make both executable.

## Rules

- Identify which harness and version you are running in. Use only features you can confirm from its built-in help, documentation or tool list. Never invent flags, hooks or APIs. If you are unsure whether a feature exists, say so and test it.
- Any wiring that changes harness configuration (hooks, plugins, scheduled wake-ups, settings files) must be project-level, inside the run directory. Show me the exact files or commands and wait for my "yes" before installing them.
- When you need me to do something (fire an event from another terminal, wait, send a message), give me the exact command with the full run-directory path, then end your turn.

## Tests

Run these in order. For each test, record what you did, what happened and the timestamps.

1. **Subagent completion.** Start two subagents. Each waits about 60 seconds (for example `sleep 60`), then replies "done". Then end your turn immediately. Questions: Are subagents synchronous (your turn blocks until they return) or asynchronous? If asynchronous, are you woken automatically when each one finishes, with no message from me? Did they run in parallel?

2. **External event wake.** Design and, after my approval, install the lightest wiring this harness supports that wakes you when `events.sh` has output. Then end your turn and tell me the `fire.sh` command to run from another terminal. Questions: Did you wake by yourself? How long after the event? What triggered it?

3. **Idle cost.** Stay idle for 10 minutes with no events. Questions: How many turns, tool calls or messages were added to your context in those 10 minutes? The goal is zero, or close to it. If your wiring polls, where does the polling run, at what interval, and what does each poll cost in context?

4. **Fresh context per wake.** Can this harness start a fresh, short-lived agent session per event, from inside this session, with no external scheduler (for example a headless or non-interactive mode)? If yes, demonstrate it once: when an event arrives, a fresh session runs `events.sh`, writes one line to `handled.log` and exits. Pass the prompt as an explicit argument, and close standard input if the command would otherwise wait for it.

5. **Conversation while waiting.** While the wiring is active and you are waiting for an event, I will send you a normal message. Questions: Did you respond normally? Did the wiring still work afterwards?

6. **Lifetime and cleanup.** Find out which process actually runs your wiring: this chat session, a harness server or background service, or something else. Show the evidence (`ps` output, process IDs, parent processes). Then answer: Does the wiring stop when this session ends? If not, what does stop it? Tell me how I stop it now.

## Report

End with:

1. A table with one row per test: capability, result (yes, no or partial), evidence.
2. The exact wiring you used: files, settings and commands.
3. Which process runs the wiring, and when it stops.
4. Limitations and unknowns, kept separate from confirmed facts.
5. Your recommendation for meeting these goals in this harness: event-driven waking, no context growth when idle, fresh context per wake if possible, nothing outside the harness, and the user always in control.

Finally, remove the wiring and the run directory unless I ask you to keep them. If the wiring runs in a process that outlives this session, say so and tell me exactly how to stop it.
````
